# Changelog

## 1.4.0 - 2026-11-18

Fixed (1.4.0-beta.16), inherited from the native SDKs (iOS and Android 1.4.0-beta.16): an event tracked just before `OptOut()` is handled the same way every time - dropped, unless a request carrying it had already started when `OptOut()` was called. The bridge passes `Track` and `OptOut` to native in call order and drops what it holds before `Initialize`, so nothing changes in the bridge. No wire changes.

Fixed (1.4.0-beta.15), inherited from the native SDKs (Android 1.4.0-beta.15): on Android, the flags refresh at app foreground is no longer lost to a `NullPointerException` when the foreground arrives while the SDK is still being constructed (the bridge initializes it from Unity's thread, not the Android main thread). A 408 on the flag exposures request is no longer re-sent at once by OkHttp; the batch waits in the native outbox. Nothing changes in the bridge, and iOS is unchanged.

Fixed (1.4.0-beta.14), inherited from the native SDKs (iOS and Android 1.4.0-beta.14): a flag exposure batch whose request failed is no longer sent a second time a few milliseconds later. It goes to the native outbox as having failed once: its first retry waits the first backoff step (4 s), or the answer's `Retry-After` when that is longer (at most 300 s), also across a relaunch of the game. The bridge only reads flags; the native SDK sends and retries the exposures, so nothing changes in the bridge.

Note for betas: during a beta, the Android dependency `io.joryio:joryio-android:<beta>` (for example `1.4.0-beta.14`) is not on Maven Central, so EDM4U cannot resolve it from there. Download `joryio-android-<beta>-maven-repo.zip` from the `joryio-android-sdk` GitHub pre-release, unzip it into a folder of its own, and add that folder as a repository - see "Testing a beta on Android" in the README.

Fixed (1.4.0-beta.13), inherited from the native SDKs: more than 100 flag exposures read before one flush are sent as several requests of at most 100 instead of only the first 100. Nothing changes in the bridge.

Fixed (1.4.0-beta.13), inherited from the native SDKs (iOS and Android 1.4.0-beta.13): a flag exposure batch whose request failed (no answer, a 5xx, a 408 or a 429) goes to the native SDK's persisted write outbox with the same `idempotencyKey` and is sent again from there, also after a relaunch; its "already sent" mark is stored only once the server takes it - beta.12 stored it before the request and never retried, so a dropped connection lost the exposure for the session. Wiping the data, a withdrawn consent and an opt-out discard the waiting batches. Nothing changes in the bridge.

Fixed (1.4.0-beta.12), inherited from the native SDKs (iOS and Android 1.4.0-beta.12): flag exposures are sent once per person, flag and variant per session across a relaunch of the game - the native SDKs keep the session's sent marks on the device and clear them on `Reset()` and `Identify()` of a different user. Nothing changes in the bridge.

Fixed (1.4.0-beta.12), inherited from the native SDKs (iOS and Android 1.4.0-beta.12): on Android the first flags, placements or cards request after the game had been idle could fail at once and never reach the server (a 1.4.0-beta.11 regression); on both platforms a placements or cards request that got no answer no longer holds the next one back for 30 s, only 3 s; and every flag exposures batch carries an `idempotencyKey`, so the server records a batch sent twice once. New constants `JoryioSDK.PLACEMENT_RETRY_AFTER_FAILURE_SECONDS` and `JoryioSDK.CARD_RETRY_AFTER_FAILURE_SECONDS` (3) mirror the native ones. Nothing else changes in the bridge.

Fixed (1.4.0-beta.11), inherited from the native SDKs (iOS and Android 1.4.0-beta.11): on Android, `Identify()` of a different user no longer carries the previous user's attributes into the new user's flags and in-app requests; flag exposures are no longer counted twice when a connection drops; and at most 20 Show when re-checks run after an outage of the event queue, on both platforms. The bridge holds no attributes of its own, so nothing changes in the bridge.

Fixed (1.4.0-beta.10), inherited from the native SDKs (iOS and Android 1.4.0-beta.10): on Android a whole-number property that arrived as a Double was sent as `3.0`; it now goes as `3`, as on iOS. And past 20 waiting Show when re-checks the oldest tracked is the one dropped. Nothing changes in the bridge.

Added (1.4.0-beta.9): "Show when" for placement campaigns (Joryio BACKLOG D465), inherited from the native SDKs (iOS and Android 1.4.0-beta.9), which build the placements request and hold an item until its moment: after N foreground seconds on the screen (the last `TrackScreen`), or once an event was tracked in this visit (the SDK then re-checks at once, after the event has left the queue, carrying it as `recheckEvent`). A held item is not in `GetPlacements` or `OnPlacementsUpdated`; at its moment `OnPlacementsUpdated` fires with it. The bridge builds no request of its own and passes the native answer through - pinned by the managed tests. `JoryioSDK.SHOW_WHEN_KINDS` has the same name and values as on every Joryio SDK (spelled like the placement constants next to it). A held-out answer's `MarkDisplayed()` before its moment is ignored natively and `OnPlacementsUpdated` fires at the moment; deferred control exposures are reported natively. `scroll` / `exit` are web-only and never shown in a game. There is no capability flag: placements exist only in the 1.4.0 betas, so an older beta (1.4.0-beta.8 and earlier) receives such a campaign and shows it as soon as the screen loads. Web adds `scroll` / `exit` and Web personalization (page edits).

Fixed (1.4.0-beta.6): a beta reports its own version. The release build writes the beta (`1.4.0-beta.6`) into `JoryioSDK.SdkVersion` of the public repository's tag, sent as `X-Joryio-SDK-Wrapper-Version`; before, every beta said `1.4.0`. The native SDKs it pins (Android through EDM4U, the iOS Swift package) report the beta in `X-Joryio-SDK-Version` too. The same fix on web, iOS, Android and React Native.

Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `OnCardsUpdated(handler)`, `OnPlacementsUpdated(handler)` and `OnFlagsUpdated(callback)` are methods that return a `JoryioSubscription`; `Cancel()` stops the updates, and `Dispose()` is the same, for `using`. This matches `JoryioSubscription.cancel()` on iOS, Android, web and React Native. `OnCardsUpdated` and `OnPlacementsUpdated` were events: replace `JoryioSDK.OnPlacementsUpdated += h` with `var sub = JoryioSDK.OnPlacementsUpdated(h)`, and `-= h` with `sub.Cancel()`. `OnFlagsUpdated` returned a plain `IDisposable`; existing `Dispose()` calls keep working. The native updates still switch on with the first handler and off with the last, and a handler added before `Initialize` is still switched on by it. Each handler now runs on its own, so one that throws no longer keeps the next one from hearing the update. Content cards: the feed type `JoryioCardFeedState` is renamed `JoryioCardFeed`. That is `CardFeed` on the other SDKs with Unity's `Joryio` prefix, as `JoryioCard` is `Card`; no Unity type collides, because Unity has no feed view. The iOS bridge imports the SDK-internal `attachCardFeedListener` as SPI. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Added: `JoryioSDK.PlacementProductElementId(productId)`, `PLACEMENT_PRODUCT_ELEMENT_PREFIX` and `PLACEMENT_PRODUCT_CARD_WIDTH` (Joryio BACKLOG D444): report a product card the game drew with `item.MarkClicked(JoryioSDK.PlacementProductElementId(product.Id))`, the `product:<id>` elementId the other SDKs' placement views report.

Added: the `time_on_screen` in-app trigger (Joryio BACKLOG D444 follow-up) works through the native iOS and Android SDKs: `JoryioSDK.TrackScreen(name)` starts the screen's clock there, and a campaign with the trigger shows after that many foreground seconds on the screen (or any screen). No C# API change; needs the native SDK versions that add it.

Added: `JoryioSDK.SetLinkHandler(Func<JoryioLink, bool>)` / `ClearLinkHandler()`: every link the native SDK is about to open - an in-app message button or link the native renderer draws, an iOS push tap - reaches C# first as a `JoryioLink` (`Url`, `Source`: `in_app` / `placement` / `card` / `push` as `JoryioLink.SourceInApp` and friends, `CampaignId`, `PlacementKey`, `ItemId`, `CardId`, `IsAppDeepLink`). Return true to take it over, false (or throw) for the native behaviour without a handler; `link.OpenDefault()` runs that behaviour later. Both bridges take the link at once (`OnLink`, at most 32 waiting) and C# answers through `CompleteLink`. A handler set before Initialize is switched on by it. New `JoryioConfig.ForwardUniversalLinks` (iOS only, default false; Android ignores it) - see the iOS SDK. The same names and source values on all five SDKs.

Added: content cards and the inbox (Joryio BACKLOG D444 Phase 3, docs/PLACEMENTS_PLAN.md section 11) - data only, since a game scene has no native view to put a feed in. `JoryioSDK.GetCards(onResult)` / `GetCards(cursor, onResult)` answer a `JoryioCardFeed` (`Cards`, `UnreadCount`, `NextCursor`, `StateScope`) of `JoryioCard`s (`Id`, `CampaignId`, `VariantId`, `Title`, `Body`, `ImageUrl`, `ButtonText`, `Url`, `Pinned`, `CreatedAt`, `ExpiresAt`, `Read`, `Clicked`); `GetUnreadCardCount()` (synchronous, from the native cache); `MarkCardViewed` / `MarkCardRead` / `MarkCardClicked` / `DismissCard` (a card or its id); `RefreshCards()`; `OnCardsUpdated(handler)` returning a `JoryioSubscription` (`Cancel()`; native updates on with the first handler, off with the last; a handler added before Initialize is switched on by it). Constants `CARD_MIN_REFRESH_SECONDS` (30) and `CARD_FEED_TTL_SECONDS` (300). Both native bridges forward to the native SDK, which fetches, caches, rate-limits, refreshes on the silent push `jry_sync: "cards"`, keeps an anonymous player's state and reports - each report goes back to the native card object the bridge handed out, which drops it after an identify / reset. The same names and wire values on all five SDKs.

Added: placements (Joryio BACKLOG D444, docs/PLACEMENTS_PLAN.md) - data only, since a game scene has no native view to put one in. `JoryioSDK.GetPlacements(keys, onResult)` answers `JoryioPlacement` (`PlacementKey`, `Items`, `IsControl`, `EmptyBehavior`, `MaxItems`, `TtlSeconds`, `MarkDisplayed()` for the holdout spot) with `JoryioPlacementItem`s (`Id`, `Kind`, `Data`, `Title`, `Body`, `ImageUrl`, `Buttons`, `MarkDisplayed()` / `MarkClicked(elementId)` / `MarkDismissed()`); `RefreshPlacements(keys)`; `OnPlacementsUpdated(handler)` returning a `JoryioSubscription` (`Cancel()`; native updates on with the first handler, off with the last; a handler added before Initialize is switched on by it). `JoryioPlacementVisibility` (a component for the RectTransform that shows an item) reports `MarkDisplayed` once `PLACEMENT_VIEWABLE_FRACTION` (0.5) of it was on screen for `IN_APP_DISPLAY_DWELL_MS` with the application focused. Constants `PLACEMENT_VIEWABLE_FRACTION`, `PLACEMENT_MIN_REFRESH_SECONDS` (30). Both native bridges forward to the native SDK, which fetches, caches, rate-limits and reports (dropping a report after an identify / reset). The same names and wire values on all five SDKs.

Added: feature flags and remote config (Joryio BACKLOG D446), routed to the native iOS and Android SDKs through both bridges, which pass the key and the default to the native getter. `JoryioSDK.GetFlag(key, defaultValue)` (object, Dictionary or List for JSON), `GetBoolFlag`, `GetStringFlag`, `GetNumberFlag` (double), `GetJsonFlag(key, defaultJson)` (JSON text) and `GetJsonFlag<T>(key, defaultValue)` (JsonUtility) return the value Joryio decided for this player, or your default before `Initialize`, before the first answer, for a flag Joryio did not send, for a value of another type, or without tracking consent. `GetAllFlags()` (logs no exposure), `RefreshFlags(onDone)` and `OnFlagsUpdated(callback)` (main thread, returns a `JoryioSubscription`: `Cancel()`, also `IDisposable`; safe before `Initialize`). The Editor stub answers the defaults. The same names (PascalCase, as for every Unity method) and wire values on all five SDKs.

Added: the game's Unity package version reaches the dashboard (BACKLOG D427). `Initialize` hands `JoryioSDK.SdkVersion` to the native SDK through both bridges, which sends `X-Joryio-SDK-Wrapper: unity` and `X-Joryio-SDK-Wrapper-Version: <version>` on every request next to its own `X-Joryio-SDK` (`android` / `ios`) and `X-Joryio-SDK-Version`. Settings > Apps shows the oldest version each app ran in the last 7 days and when a newer SDK is out. Not a game setting. In the Editor (the stub) nothing is sent, as before. The same wire names on all five SDKs.

Added: `JoryioSDK.ResetTo(anonymousId)`, through both native bridges (the native SDK checks the id; a null id crosses as empty, which is refused) - everything `Reset()` does, then the anonymous id you pass instead of a random one, for an app that keeps its own visitor id (BACKLOG D366). The id must be 8 to 255 letters, digits, `.`, `_`, `:` or `-`, must not have the shape of a Joryio profile id (24 lowercase hex) and must not be the user id the SDK holds; a refused id is logged and the call is a plain `Reset()` (a random id), so a logout is never skipped. The same name and rule on all five SDKs. No wire changes: the server sees an ordinary anonymous id. Like `Reset()`, `ResetTo` drops a click-link token the SDK has not sent yet (one held while consent is pending), so the link is never attributed to the next player on the device.

Changed (BACKLOG D366, before any release of resetTo): it also refuses the anonymous id the SDK holds while a user is signed in - that id is tied to the signed-in person's profile, and adopting it would hand their in-app messages, events, form attribution and push subscription to the next person on a shared device (a random id is used instead). `ResetTo(anonymousId, Action<bool> onResult = null)`: `true` adopted, `false` refused or not run; both native bridges answer through the request id. The same on all five SDKs.

Changed (BACKLOG D366): `resetTo` also refuses the last 20 anonymous ids this device held for a signed-in user when a reset signed them out (stored locally, newest kept; `wipeData()` forgets them) - a random id is used and it answers `false`, the same message and cap on all five SDKs. Unchanged: a call that never reaches native answers `false`, once - now the same on Android, iOS and React Native.

Added: `JoryioSDK.IdentifyFromLink(string url)`, through both native bridges (the url is passed through unchanged; native reads the token and applies the rules) - click-link identity. `Initialize` also checks `Application.absoluteURL` (the link that launched the game) and listens to `Application.deepLinkActivated`, so a game with deep links set up needs no code. When the URL carries the `jr_t` token a tracked Joryio message link adds, the native SDK sends it to `POST /v1/identify-link`. The server uses it only to attribute this game's session and later events (Session Start, screen views, conversions) to the contact the message was sent to - it never identifies the person: the game's profile does not become the contact and is never merged into it, and nothing set in the game is written to the contact. Only `Identify` joins the two. Nothing happens when a user is identified, the player opted out or consent is denied; while consent is pending the token is held in memory and sent when consent is granted. A call before `Initialize` is ignored, like other data calls (the launch URL is read by `Initialize`). The same name, parameter, path and body on all five SDKs.

## 1.3.3 - 2026-11-03

Fixed (from the iOS and Android SDKs this package uses): an in-app message the native SDK draws counts as displayed only once someone could have seen it. It is shown only on a screen that is in the foreground and not mid-transition or closing, and `in_app.displayed` is reported - and the campaign's frequency cap spent - only after it has been on screen for `JoryioSDK.IN_APP_DISPLAY_DWELL_MS` (1000 ms) with the app in the foreground. A tap or a close before then counts as seen (displayed first, then the click or dismissal); a message that leaves the screen sooner is not counted and stays eligible.

Added: `JoryioSDK.IN_APP_DISPLAY_DWELL_MS`. If the game draws in-app messages itself (`SetInAppMessageHandler`), call `MarkDisplayed()` by the same rule: after the dwell, or right before `MarkClicked` / `MarkDismissed` if the player acts sooner - not as the message is first drawn. No bridge or wire changes.

## 1.3.2 - 2026-10-25

Added: `JoryioConfig.HoldInAppMessagesForHandler` (off by default; wire key `holdInAppMessagesForHandler`). `SetInAppMessageHandler` can only be called after `Initialize`, and the first sync could finish before it, so the native SDK drew that message itself when its UI was in the build. With the option on, a message that is ready before the handler is set is held - not drawn, not reported, nothing spent - and handed to the handler when it is set; `ClearInAppMessageHandler()` instead ends the hold and the native SDK draws the held message. The same option, by the same name, on iOS, Android and React Native.

## 1.3.1 - 2026-10-24

Changed: on iOS the native SDK is now a Swift package, not a CocoaPods pod. The iOS post-build step adds `https://github.com/joryio/joryio-ios-sdk.git` at exactly this version to the exported Xcode project and links the `Joryio` product into `UnityFramework` (and `JoryioUI` as well when the `JORYIO_IOS_UI` scripting define is set). `Editor/JoryioDependencies.xml` now lists only the Android artifact; External Dependency Manager is no longer involved on iOS. Upgrading from 1.3.0, which used the `Joryio/Core` pod: build the iOS player once with **Replace** rather than **Append**, and delete any `<iosPod name="Joryio/...">` line from your own External Dependency Manager files.

Later **Append** builds keep the package in step: the Swift package reference is moved to the version of the installed Unity package, and `JoryioUI` is linked when `JORYIO_IOS_UI` is set after the first export. Removing the define needs a Replace build to unlink `JoryioUI`; the build log says so.

Added: `JoryioInAppMessage.MaxWidth` for HTML modals and slide-ups (null for every other message), forwarded by both native bridges. When you draw messages yourself, give your web view min(MaxWidth, screen width - your margins) before the content lays out and measure the height from `document.body` (with `body{display:flow-root}`), not the root element, whose height never drops below the web view's own.

Fixed (when the native SDK draws messages: `joryio-android-ui` on Android, the `JORYIO_IOS_UI` define on iOS): HTML in-app messages did not work on Android since 1.3.0, and native HTML modals and slide-ups could grow but never shrink. See the iOS and Android release notes.

No other C# API changes.
